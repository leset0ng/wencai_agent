## 1. 设计原则

**大模型负责"理解与提议"，确定性代码负责"授权与执行"。** 模型的任何输出都被视为不可信的提议。

| # | 硬约束 | 实现位置 | 状态 |
|---|---|---|---|
| 1 | 风险等级只能由代码判定，且只升不降 | `server/policy/engine.ts`、`rules.ts` | ✅ |
| 2 | 系统中不存在任何可被模型调用的"确认 / 放行 / 验证"工具 | `server/agent/tools.ts`；`tests/confirmation-boundary.test.ts` 守护 | ✅ |
| 3 | 关键数据不经模型转述：余额、确认单、回执由服务端数据渲染为固定组件 | `components/chat/ConfirmCard.tsx`、`server/genui/validate.ts` | ✅ |
| 4 | 外部文本一律视为数据 | `server/guard/`、`server/tools/sanitize.ts` | ⚠️ 只审核最后一条用户消息、对话历史可伪造，见 §18 #3 |

两条用于评估新功能的判据：

1. **模型可以提供"事实"，不能提供"策略"。** "收款账户近期异常"是事实，可以进入 `PolicyFacts`；"这笔要强验证"是策略，只能来自 `rules.ts`。
2. **模型生成的文本永远不能成为证据。** 数字核验的出处只有：服务端会话快照、本轮工具输出、服务端执行回执。

## 2. 威胁模型

### 2.1 需要保护的资产

账户余额与流水、交易授权、卡号与卡密码、强验证凭据、审计记录的完整性、其他用户的数据。

### 2.2 攻击者与攻击面

| 攻击者 | 能力 | 主要防线 |
|---|---|---|
| 恶意的当前用户 | 构造任意对话内容、篡改浏览器提交的对话历史、直接调用 API | 策略引擎、确认链路、身份只来自会话 |
| 恶意的其他用户 | 控制自己的注册户名、AA 事由、转账备注等会出现在受害者对话里的文本 | 外部文本隔离、Guard |
| 被劫持或产生幻觉的模型 | 调用任意已注册工具、生成任意文本 | 工具白名单、策略引擎、数字核验、无确认工具 |
| 外部数据源 | 返回畸形或恶意的基金数据 | 格式校验、不执行远程脚本、大小与时间限制 |
| 拿到数据库写权限的人 | 直接修改记录 | 审计哈希链（⚠️ 无密钥，见 §18 #6） |

### 2.3 信任边界

```
浏览器（不可信：对话历史、按钮消息、表单）
  │  Cookie 会话 → 唯一的身份来源
  ▼
服务端 API（认证、来源校验、参数校验）
  │
  ├─▶ 模型（不可信：只能提议）
  │     └─▶ 工具 → runner.ts（唯一授权入口）→ 策略引擎（可信）
  │
  └─▶ 确认 / 安全页面（只对已登录用户开放，模型无法调用）
        └─▶ 结算事务（最终复查）→ 审计
```

## 3. 权限分级

### 3.1 风险等级规则

规则定义在 `server/policy/rules.ts`，逐条应用，**只能升级或拒绝，不能降级**。每条命中的规则都会记录原因并写入审计。

| 规则 ID | 适用操作 | 条件 | 结果 | 状态 |
|---|---|---|---|---|
| `recipient-account-risk` | 转账类 | 收款账户被人工复核为高危（`confirmed`） | **拒绝** | ✅ |
| | | 收款账户被 AI 标记为可疑（`suspected`） | 升为红色 | ✅ |
| `life-payment-authorization` | 商城购买、开通订阅 | 单笔超过 3000 元，或开启自动续费 | 升为红色 | ✅ |
| `sensitive-card-operation` | 卡片变更 | 解锁、挂失、调整限额 | 升为红色 | ✅ |
| `account-locked` | 所有非只读操作 | 账户处于锁定期 | **拒绝** | ✅ |
| `transfer-burst` | 转账类 | 10 分钟内已有 5 笔转账 | **拒绝**（熔断） | ✅ |
| `transfer-daily-total` | 转账类 | 北京时间自然日、跨本人全部账户累计（含本笔）**超过 1000 元** | 升为红色 | ✅ |
| `transfer-single-large` | 转账类 | 单笔**超过 3000 元** | 升为红色，并要求双重验证 | ✅ |

各工具另有基础等级：只读查询为绿色；写操作至少为黄色；挂失、解锁、调整授信额度、AA 付款、基金申购、创建常设授权等为红色。`tests/planning-tools.test.ts` 保证没有写工具是绿色。

**执行时复判** ✅：用户确认时，`confirmPending` 在用户执行锁内重新采集事实、重新判级，等级只取更高者。确认单签发后才发生的累计超额或风险标记，确认时同样生效。

**结算时最终复查** ✅：`settleTransfer`、信用卡还款、生日订单在**扣款事务内**再次检查日累计额度；转账结算前还会再查一次收款账户风险标记。这样即使一张旧的黄色确认单拖到跨过额度后才确认，也无法扣款。

### 3.2 渠道能力上限

| 渠道 | 可就地完成的最高等级 | 超出时 | 状态 |
|---|---|---|---|
| Web / H5 | 红色 | — | ✅ |
| 飞书 | 黄色 | 红色操作推送一次性 H5 链接；黄色操作确认时若需要卡密码或已升为红色，同样回复原确认单的 H5 链接 | ✅ `lark-confirm.test.ts` |
| MCP | 绿色（只读） | 不注册任何写工具和 `plan_task` | ✅ |

### 3.3 验证方式矩阵

| 场景 | 要求 | 状态 |
|---|---|---|
| 黄色常规转账 | 付款卡交易密码、短信、模拟指纹、模拟人脸，**任选其一** | ✅ |
| 红色转账（日累计超过 1000 元、AA 付款等） | 有银行卡时先验证卡密码，再完成短信或模拟指纹 / 人脸 | ✅ |
| 单笔超过 3000 元，或收款账户被标记为可疑 | 付款卡交易密码 **加** 模拟指纹或人脸；短信不能替代第二步 | ✅ |
| 收款账户被确认为高危 | 拒绝，无法通过任何验证放行 | ✅ |
| 其他红色操作（挂失、解锁、调额、申购等） | 关联卡片时先验证卡密码，再完成额外的强验证 | ✅ |
| 申请新卡 | 在独立安全页面为新卡设置专属交易密码后才发卡 | ✅ |

**关于 Passkey**：`server/auth/passkey.ts` 保留了完整的 WebAuthn 实现，服务端的强验证仍接受 Passkey，但当前交易页面不展示这个选项，双重验证的第二步也不接受它。原因是 WebAuthn 无法可靠区分用户用的是指纹、人脸还是设备 PIN。

## 4. 确认与强验证链路

### 4.1 待确认动作（pending action）✅

```
模型调用写工具
  └─▶ runner.ts：参数校验 → 采集事实 → 判级
        ├─ 绿色：直接执行
        └─ 黄 / 红：创建 pending_actions
              · 参数快照与参数哈希
              · integrity = HMAC(密钥, id | userId | 工具 | 参数哈希 | 等级 | 过期时间)
              · 摘要由服务端根据已校验参数生成，不使用模型文字
              · 默认 300 秒过期
```

确认时依次校验：归属当前登录用户 → HMAC 完整性 → 未过期 → 未消费 → 关联计划未暂停 → 执行时复判 → 卡密码凭证 → 强验证 → **原子消费**（条件更新，并发重复提交只有一个成功）→ 执行 → 审计。

相关测试：`integrity.test.ts`（改金额、换收款人、红降黄、换用户、延长时效均被识别）、`authorization.test.ts`、`confirmation-result.test.ts`。

### 4.2 业务预览令牌 ✅

`preview_*` 工具签发、`commit_*` 工具消费，绑定用户、操作类型和**已解析实体 ID 的参数指纹**，15 分钟有效，单次消费。它保证"提交的参数与预览时一致"，**不代表用户已授权**；授权仍由 4.1 的待确认动作完成。相关测试：`confirmation-token.test.ts`。

### 4.3 独立安全页面 ✅

所有密码、短信、指纹、人脸验证都在独立安全页面（`/secure-operation`）完成：

- 安全请求绑定用户、**当前登录会话**、具体动作，5 分钟有效，单次消费；
- 验证结果只在服务端记录，页面关闭后对话中只核对银行回执；
- 模型不接触密码，也不能代替用户提交；
- 接口带来源校验和 `no-store` 缓存头。

### 4.4 每张卡独立的交易密码 ✅

- 每张卡单独设置密码，scrypt 加随机盐存储；
- 修改卡密码需要先通过强验证；
- 卡密码验证凭证绑定卡片 ID 和**密码版本号**：确认前改过密码，旧凭证即失效；
- 新卡的密码在发卡事务内落库，凭证用后立即清除。

相关测试：`per-card-security.test.ts`、`onboarding-card-number.test.ts`。

### 4.5 短信验证码 ✅

- 验证码只用 HMAC 存储，绑定用户和操作范围（scope）；
- 5 分钟有效，最多尝试 5 次，单次消费；
- 发送频率：60 秒内最多 1 次，10 分钟内最多 5 次；
- 只发往已验证的绑定手机号；
- **交易验证码不会打印到日志**：没有配置 `SMS_DELIVERY_URL` 时，短信验证不可用。

### 4.6 模拟生物验证 ✅（演示用途）

- 只在 `AUTH_DEMO_MODE=true` 时可用；生产环境默认关闭，演示环境需要显式开启；
- 每次验证生成一次性挑战，绑定用户、操作范围和方式（指纹或人脸），5 分钟有效，单次消费；
- 界面明确标注"模拟"，不声称进行了真实生物识别。

### 4.7 熔断锁定 ✅

强验证或卡密码连续失败 5 次，账户锁定 30 分钟，写入 `circuit_breaker` 审计。锁定期间所有非只读操作被策略引擎拒绝。

### 4.8 改密凭证 ✅

账户级的 `request_password_change` 工具**不接收任何密码参数**：确认后只签发一个 5 分钟有效的一次性凭证，用户在设置页亲自输入新密码。审计只记录"发生了修改"，不记录密码或其哈希。

> 当前 Agent 已不再注册这个工具（`availableBankTools` 将其排除），改由按卡修改密码的 `card_password_settings` 引导用户到安全页面完成。实现与测试仍保留。

## 6. 提示词注入防御

### 6.1 输入审核（直接注入）⚠️

- `server/guard/heuristic.ts`：匹配前先做 NFKC 规范化，并去掉不可见字符（零宽、方向控制、软连字符等）和全部空白，防止用换行、空格、全角字符拆开关键词；
- 规则覆盖"忽略规则"（含"不要理会先前的指示"等同义说法）、角色劫持、套取系统提示词、绕过验证、伪造系统消息；
- "绕过验证"分两档：明确要求跳过 / 绕过验证、声称风控已关闭、"免确认 + 直接执行"的组合指令直接**拦截**（同一句内紧跟问句时，如"不用验证码，直接转账可以吗？"，视为询问规则，只**标记**）；单独的"不用确认""不需要验证"只**标记**并写审计，避免把"先不要确认，我再想想"这类日常说法整句拒答（真正的验证由确认链路强制执行，任何话术都绕不过去）；
- "请不要跳过确认""禁止绕过安全验证"等要求保留验证的说法会先被识别并排除，不会误判；
- 可选接入 Qwen3Guard，与规则**并行执行、取更严格的结果**；审核模型超时或不可用时退回规则判定，不阻断业务；
- 判定为拦截的消息**不进入模型**，直接返回固定拒答文案。

相关测试：`guard.test.ts`（变形绕过、必须拦截、不得整句拒答三组样本）。

**缺口**：
- 正则无法穷举同义改写。实测"抛开前面的所有约束""之前的指令全部作废"、英文 "disregard"、中英混写、拼音、繁体"規則"、"从现在起你是银行行长"仍被规则放行，需要依靠 Qwen3Guard 兜底；
- 只审核最后一条用户消息，见 §18 #3。

### 6.2 工具输出清洗（间接注入）✅

- `sanitizeToolOutput`：工具输出中外部可控字段的文本先过 Guard，可疑内容（拦截或标记）替换为"[已屏蔽可疑内容]"并写审计；
- **确认单摘要同样清洗**：`runner.ts` 在把确认单交给模型和前端前，对摘要再做一次清洗，防止对方填写的 AA 事由、户名经由摘要的 `value` 字段进入模型；
- `quarantineForModel`：交给模型的外部文本加上 `⟦外部文本⟧…⟦/外部文本⟧` 隔离标记，文本中自带的方括号标记会被转义，无法伪造结束标记逃出隔离块；
- 外部字段清单 `UNTRUSTED_FIELDS`：`counterparty`、`memo`、`merchant`、`description`、`remark`、`accountName`、`recipient`、`address`、`refundReason`、`institution`、`title`、`requesterName`、`alias`、`note`、`payeeName`、`name`、`value`。
- 目录类工具豁免通用键：基金白名单（`rank_funds`、`list_funds`、`get_fund_metrics`、`get_fund_details`、`get_wealth_advice`）、`list_products`、`list_life_catalog` 的输出全部来自服务端维护的目录，用 `catalogFields` 声明其 `name`/`title` 不过审核、不加隔离标记，避免长列表逐条调用审核模型和误屏蔽。只能豁免这三个通用键，其他外部字段与确认摘要始终审核；漏声明只影响性能，不影响安全。同一次输出中重复的文本只审核一次。

相关测试：`tool-output-isolation.test.ts`（各字段与确认摘要的完整路径、标记逃逸）、`server-copy-guard.test.ts`（扫描全部服务端中文文案，保证不会被清洗误伤）。

### 6.3 结构性防线 ✅

即使以上两层都被绕过，以下限制依然成立：

- 工具签名里没有 `userId`，无法越权到其他用户；
- 没有确认工具，模型最坏只能生成一张用户不会去点的确认单；
- 风险等级、验证方式由代码决定；
- 确认结果核对轮次只开放只读工具。

### 6.4 子模型的输入隔离 ✅

- **理财专家**：模型只看到"候选1 / 候选2"这样的别名和数字指标，**看不到基金名称**；
- **收款风险分析**：模型只拿到 SQL 聚合出的数字特征，看不到姓名、账号、备注、商户名；
- **用户画像文案**：模型只拿到格式化好的指标，没有对手方名称等外部文本。

## 8. 资金与事务安全

### 8.1 通用机制 ✅

- 金额统一以整数分存储；
- 扣款用**条件更新**（`余额 ≥ 金额` 才更新），不会出现负余额；
- 文财行内转账**双边记账**：付款方扣款与收款方入账在同一事务，各自生成流水；
- 用户执行锁（数据库租约）协调网页与 worker 等多进程；SQLite 繁忙时有界重试；

## 13. 模型与外部数据

### 13.1 模型故障切换 ✅

主模型在**开始响应之前**失败（连接错误、限流、服务端错误、15 秒内无响应）时切换到备用模型，失败的模型冷却 60 秒。用户主动取消不切换。切换只影响"由谁提议"，分级与确认不变。相关测试：`model-failover.test.ts`。

**边界**：流开始后中途断开**不切换**，因为此时可能已有工具调用发出，重跑会重复执行。

### 13.2 基金数据接入 ✅

- 数据源为天天基金公开接口，另有离线快照兜底；
- **远程 JS 文件只当文本处理**，用正则提取少数字段，绝不执行；
- 禁止重定向、响应大小受限、请求 12 秒超时、单次最多 100 条净值；
- 数据入库前校验格式；
- **基金风险等级为人工配置**（`server/funds/pool.ts`），不来自数据源，也不来自模型；
- 净值过期时禁止申购；页面和回复标注"公布净值，非实时成交价"。

相关测试：`fund-data.test.ts`。

## 20. 对外表述口径

答辩、视频和文档请统一使用以下说法，避免过度承诺：

- **核心表述**："风险等级和验证要求由策略引擎强制执行；模型的输出只是提议，没有确认能力。"
- **生物验证**："演示环境使用明确标注的模拟指纹 / 人脸按钮代替设备采集；验证的触发条件和'密码 + 生物验证'的组合要求由代码强制执行。生产环境替换的只是验证这一步，分级与确认链路不变。"
- **防幻觉**："关键数据走固定组件，回复中的金额和流水先核验再展示。"不要说"杜绝幻觉"或"零幻觉"。
- **防注入**："审核、隔离标记、结构性限制三层防护；即使前两层被绕过，模型也无法越权或放行交易。"不要说"防住了所有注入"。
- **审计**：完成 §18 #6 之前，只说"可发现对记录的直接篡改"，不要说"数据库被攻破也无法篡改"。
- **基金数据**："最新公布净值，截至某日"，不要说"实时行情"；申购是"模拟银行内申购"。
- **反诈**：完成 §19 B 之前，只说"收款账户风险标记与人工复核"，不要说"已具备反诈劝阻"。
