# 多笔转账交互修复

复现场景：`给妈妈转400再给王芳转200再给房东装600`。旧实现把多个收款人放进同一个选择位置，又使用只选择对象的 select 模板，导致确认消息只剩一人和一张卡，丢失全部转账金额；金额校验也不支持省略“元”。

## 当前流程

1. Agent 调用只读 `prepare_transfer_batch`，按当前原文提供每笔 `recipientQuery`、`amountYuan` 和可选 `note`（最多8笔，备注最多50字）。服务端校验人名与金额对应关系、不允许复用同一原文金额制造重复步骤、不能漏掉可识别的转账句。
2. 工具内置逐笔 `find_payee` 与正常储蓄卡查询。每笔都有独立 stepId、候选集合和金额，多个同名对象仍分别选择；唯一对象灰显。找不到对象或缺少付款卡时明确提示待补充项，不降级到丢失目的的 select。
3. `BatchTransferView` 复用现有收款人选择、银行卡轮播、SelectionDraft、统一确认与取消。选择和取消不发送消息；只有确认才汇总每笔收款人/银行/脱敏账号/金额/备注与共用付款卡尾号。按钮保留，可取消后重选。
4. 确认消息固定表述为“我确认从…依次办理以下…笔转账”，不复制历史用户原话，不携带密码、验证断言或执行凭证。即使没有旧聊天上下文，Agent 仍能重新查询并创建有序DAG，等待每笔独立安全验证。准备界面不能授权扣款。

多笔模板由服务端专用准备工具构造，普通 `prepare_interaction` 仍只接受单步模板。旧查询组件、重复批次视图及模型重复表格不会与完整多笔选择界面同时展示；银行确认单优先于选择界面。

`requestedAmounts` 支持“给妈妈转400”“转400给妈妈”等口语金额；裸手机号、卡尾号及日期不会作为金额。输出核验继续只信任服务端快照及本轮工具结果，多笔准备工具返回经逐笔核对的人名和金额。用户原话不直接作为余额、账户归属或交易成功的证据；卡尾号和成功声明仍按原有规则核验。

## 验证证据

- `tests/batch-transfer.test.ts`：截图三笔需求、消歧隔离、重复/遗漏步骤拒绝、金额交换拒绝、不可用卡过滤、缺信息提示、历史重选、模板优先与去重、裸金额及证据边界。
- 真实模型：仅调用一次准备工具就返回三笔完整界面；只给确认消息、不附旧聊天上下文，重新查询后正确生成400/200/600元的三笔银行确认单，数字核验零违规。也验证过有序DAG路径：三个转账节点保留完整参数，首笔停在银行确认。最新证据保存在 `.scratch/batch-transfer-model-proof.json` 与 `.scratch/batch-transfer-confirmation-proof.json`。
- 浏览器414×896：选择后发送0条，统一确认后发送1条完整消息；取消不发送，重新选择可继续用原确认按钮。截图 `.scratch/batch-transfer-browser.png`。
- 所有模型与数据库验证使用 `.scratch/batch-transfer-preview.db` 隔离演示库；不输入交易密码、不执行转账，验证前后余额保持不变。
- 最终47个测试文件、529项测试通过，类型检查与生产构建通过。
