# HTTPS 部署后的“请求来源无效”修复

## 原因与证据

公网地址为 `https://wencai.35-247-141-61.sslip.io`。Caddy 终止 TLS 后，以 HTTP 转发到 `wencai-web:3000`；Node/Hono 交给路由的 `request.url` 因此是内部 HTTP 地址。浏览器提交的 `Origin` 则仍为公网 HTTPS 地址。

原接口通过 `origin !== new URL(request.url).origin` 判断跨站。正常 HTTPS 操作也会被拒绝，日志表现为：`POST /api/payments 200`（生成转账确认单），紧接着 `POST /api/secure-operation 403`（打开安全验证失败）。

这是生产部署接入与来源校验未匹配的问题。此前部署检查验证了登录、查询与 Agent，但未覆盖 HTTPS 代理后的敏感业务入口。

## 文件与处理

| 文件 | 问题或修复 |
|---|---|
| `scripts/serve.mjs` | 生产 Node 入口接收代理的 HTTP 请求。该内部协议是正常部署方式，不能直接代表浏览器来源。 |
| `src/routes/api/secure-operation.ts` | 原内部 URL 比较误拦截转账核对、银行卡安全验证和卡密码管理；改为统一来源校验。 |
| `src/routes/api/card-number.ts` | 同样的比较误拦截查看完整卡号；改为统一来源校验。 |
| `src/routes/api/onboarding.ts` | 同样的比较影响旧版初始设密入口；改为统一来源校验。 |
| `src/server/security/request-origin.ts` | 新增公共校验：以配置的 `PUBLIC_BASE_URL` 为可信公网来源，不信任客户端可伪造的 Host、Forwarded 或 X-Forwarded-*。 |
| `tests/request-origin.test.ts` | 覆盖 HTTPS 浏览器 → HTTP 上游、三个实际接口、伪造代理头、跨站来源、端口/协议不同和本地开发别名。 |

来源校验并未关闭。公网只允许配置的来源；真正跨站请求仍返回 403。无 Origin 的原生客户端继续兼容，但明确带 `Sec-Fetch-Site: cross-site` 的请求被拒绝。本地开发仅允许配置的 localhost/127.0.0.1 同协议、同端口别名。

## 验证方式

来源专项测试使用内部 `http://wencai-web:3000` 请求 URL 和真实公网 HTTPS Origin。合法来源应进入认证阶段，未登录返回 401；恶意来源在认证和业务操作前返回 403。

部署验证须额外覆盖：登录 → 生成转账确认单 → 创建独立安全请求 → 读取验证页面信息 → 取消测试确认单，并检查业务余额和流水没有变化。完整验证与扣款测试使用隔离数据库，不在实际用户账户上试扣款。

本修复最初直接部署 Google VM，未单独提交或推送 GitHub；随后随本地功能合集按用户要求上传仓库。部署时保留公网 HTTPS、演示模式及现有业务数据。

## 已完成的验证结果

- 44 个测试文件、493 项回归，以及 4 项部署专项测试通过；类型检查和生产构建通过。
- 云端隔离数据库中，完整 HTTP 流程完成 1.23 元账户互转，付款/收款余额变化正确，重复读取回执不重复扣款；测试容器已停止。
- 正式 HTTPS 站点完成登录、生成转账确认单、创建独立安全请求、读取核对摘要、取消请求和取消确认单；实际账户余额保持不变。
- 三个接口对恶意跨站来源仍返回 403；同源查看卡号/旧版设密的无效输入进入业务参数校验并返回 400，不再误报来源无效。
