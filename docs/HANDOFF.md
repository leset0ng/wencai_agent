## 0. 三十秒版本

单仓全栈 TypeScript 应用：**用自然语言办理银行业务的 AI Agent**。TanStack Start + React 19 + Vite + Tailwind 4 + SQLite/Drizzle + Vercel AI SDK v7 + DeepSeek。

**唯一的架构原则，也是一切设计推理的起点：**

> **大模型负责"理解与提议"，确定性代码负责"授权与执行"。**

模型的输出被视为**不可信的提议**。它可以决定调哪个工具、传什么参数、怎么展示；它**不能**决定这笔操作的风险等级、是否需要确认、是否被允许执行。所有涉及资金与账户状态的判定都由纯代码完成（`src/server/policy/`）。

**接手时请先接受这条原则，再用它检验你写的每一行代码。** 本仓库里几乎每个看起来"绕远路"的设计，都是这条原则的直接推论。

## 1. 四条硬约束（违反即视为回归）

| # | 约束 | 代码位置 | 违反会怎样 |
|---|---|---|---|
| 1 | **风险等级只能由代码判定，且只升不降** | [engine.ts](../src/server/policy/engine.ts)、[rules.ts](../src/server/policy/rules.ts) | Prompt 注入即可绕过风控 |
| 2 | **不存在任何可被模型调用的"确认/放行"工具** | [agent/tools.ts](../src/server/agent/tools.ts) 的工具集 | 模型可自行放行资金操作 |
| 3 | **关键数据不经模型转述** | [ConfirmCard.tsx](../src/components/chat/ConfirmCard.tsx)、[genui/validate.ts](../src/server/genui/validate.ts) | 模型可编造余额/回执 |
| 4 | **外部文本一律视为数据** | [guard/](../src/server/guard/)、[tools/sanitize.ts](../src/server/tools/sanitize.ts) | 备注/商户名成为注入通道 |

**推论摘要**（这些都已实现，不要"优化"掉）：
- `userId` 只从 `getSession(request)` 取得，写进 `AgentContext`；**工具签名里根本没有 userId 参数**，模型无法指定"帮谁办"。
- 刚登录过**不能**免除 🔴 操作的单笔 step-up。登录证明"你会用这台设备"，🔴 证明"这一笔是你本人同意的"。
- 渠道身份绑定（飞书 open_id ↔ 银行用户）只解决"你是谁"，**不提升权限上限**。

### 5.1 理财专家：设计与约束

**用户需求**：用户问理财产品时，路由到"理财专家"，分析需求给出建议。

**这个方向是对的**，因为它落在**只输出建议、不移动资金**的域里。但必须先接受下面的约束，否则会弄脏安全叙事。

**必须改的一点：专家不能决定风险等级，也不能签发确认。**

风险匹配逻辑已存在且是纯代码：
- [bank-extended.ts:32](../src/server/tools/bank-extended.ts) `riskGate()`：用 `RISK_ORDER` 硬比较产品评级与用户 `riskRating`
- [jobs.ts:18](../src/server/tools/jobs.ts) `scoreRisk()`：按问卷五项答案算出 R1–R5

**如果"理财专家"能自由生成文本，它可以说"您是稳健型，可以买 R4"。这句话没有约束力（`riskGate` 照样拦），但会让评委以为风险分级是模型判断的**——把最大技术优势讲反了。

**目标形态**：

```
路由：agent/run.ts 内判定 intent=wealth
  └─▶ 只读顾问（独立模型调用，不接管主循环）
        工具集：list_products / resolve_product / check_product_eligibility
                get_holdings / riskGate（只读部分）
        输出：结构化 advice 对象，不是 Markdown
              { matchedProductId, horizon, liquidityTradeoff,
                conflicts: string[], riskGate: <复用服务端结果> }
        ↓
      固定 React 组件 AdviceCard 渲染（数字只能 $state 引用）
        ↓
      用户点"看产品详情" → 发一条普通用户消息 → 重走 完整意图→策略→确认
```

**三条硬约束（写进代码注释）：**

1. **专家不能调用任何写工具。** 在 [agent/tools.ts:16](../src/server/agent/tools.ts) 的 `availableBankTools` 之后，再按 `expert` 字段裁剪一次工具子集。
2. **专家的推荐必须引用 `riskGate` 的服务端结果**，不能自己算匹配。若推荐产品的 `riskGate.eligible === false`，**服务端直接丢弃该条推荐**，不展示、不解释。
3. **专家不签发确认单。** 申购仍是 `preview_purchase` → `pending_actions` → 用户确认 → `/api/confirm`。专家输出中任何"已为您申购"都会被 `verify/response.ts` 拦掉（现在这套已经能拦，不要绕开）。

**这个设计真正解决的产品问题**（答辩时这么说）：
现在用户说"我想存一年的定期理财，有点闲钱"，Agent 调 `recommend_products`，拿回的是**产品库视角**的列表。专家的价值是把需求翻译成约束并解释取舍：

|---|---|---|
| "一年后要用" | 期限 ≤ 365 天 | `products.termDays` 有字段，但无人做映射 |
| "要能随时取" | 锁定期 = 0 | |
| "稳一点" / "收益高一点" | 风险上限 vs 风险偏好 | 需区分**硬顶**与**偏好** |
| "5 万块闲钱" | 金额下限过滤 | `products.minAmountCents` |

**最有价值的是 `conflicts`**：用户说"要稳、要随时取、还要年化 5%"时，指出这三者不可能同时满足，并说明放弃了哪个。纯推荐列表永远做不出这个，也是最容易被记住的一击。

## 7. 关键实现细节与坑（**改代码前必读**）

1. **建表语句是幂等的无损升级，不是迁移框架。** `cards/service.ts` 首次读取卡片时会升级旧库：共用账户的第一张储蓄卡保留原账户 ID/余额/流水，其余共用卡建零余额账户。**可重复、可并发执行，绝不运行 seed 或重置用户数据库。** 当前用 `drizzle-kit push` 同步结构，**没有版本化迁移目录**。
2. **SQLite 事务限制**：客户端请求排队避免连接池在事务 `await` 期间争锁；**事务回调必须只使用 `tx`，不能调用外层 `db`**；**事务内不得包含网络请求等外部副作用**。跨进程通过数据库用户租约 + 有界锁冲突重试协调。
3. **审计哈希链**：载荷必须先归一化为 JSON 再算哈希，否则 `Date` 等对象写库前后序列化结果不同，会导致整链校验误报。读前序与写新记录**必须同一事务**。
4. **json-render 的 props 校验不可单独依赖**：实测 `catalog.validate` 会放行写在对象型 prop（`{$state}`）位置上的数字字面量。因此 `server/genui/validate.ts` **额外**做了"spec 中禁止任何数字字面量"的显式检查（纵深防御），并补齐模型常省略的 `children`。
5. **数字核验只信任三种出处**：服务端会话快照、本轮工具输出、服务端执行回执。**浏览器提交的历史工具结果不作为凭证**（`agent/run.ts` 的 `trustedEvidence`）。
6. **确认回报轮次降级为只读**：带 `confirmedActionId` 的请求 `readOnly: true`，不注册 `plan_task` / `show_view`，防止重复写操作。
7. **待确认动作的消费是原子的**，条件更新防并发重复消费；`confirmPending` 在**用户执行租约内重跑风险策略**（等级只升不降，按执行时事实判断）。
8. **扩展转账的已知缺口**：`commit_transfer` 尚未接入原 `transfer` 的风险升级规则。`ARCHITECTURE.md` 与 `README.md` 均已标注。
9. **不是每个 write 工具都有补偿**；缺失补偿或补偿失败时计划进入 `failed`，**不能承诺所有流程都自动回滚成功**。
10. **后台 `/admin` 不经过策略引擎与确认令牌**，是人工直连通道，每条命令写审计（`admin_command`）。它**不是用户端**，且 `ADMIN_TOKEN` 是演示访问凭据，**不是完整管理员角色系统**。
11. **进程内状态有三处**：生成式 UI 快照（`agent/session.ts` 的 Map）、飞书对话历史、Passkey challenge。**正式多实例部署需共享持久化。**
12. **`routeTree.gen.ts` 是生成文件**，新增路由后运行 `pnpm generate-routes`，不要手工维护。

### 2026-10-12 · P0 补 `request_password_change` ✅

赛题把"密码修改"明确列入红色操作示例，此前只能走 `/settings` 页面，Agent 拿不到。现已补上，**并顺手解决了一个真实的安全问题**。

**核心约束：新密码绝不经过模型。**

最直觉的写法 `request_password_change({ newPassword: '123456' })` 是错的——密码会同时落进三处：
模型上下文、`pending_actions.args_json` 参数快照、`audit_logs` 载荷。这与 §0 的"关键数据不经模型转述"直接冲突。

**实际实现拆成两步，模型只参与第一步：**

```
用户说"我要改交易密码"
  └─▶ request_password_change（★ inputSchema 为空，不接收任何密码）
        └─▶ 红色确认单：明确告知"新密码在安全设置页输入，不经过 AI"
              └─▶ 用户在独立安全页完成额外验证（演示指纹 / 人脸需显式开启演示模式）
                    └─▶ 签发一次性凭证 pwg_*（5 分钟、单次消费、绑定用户）
                          └─▶ /settings?pwTicket=pwg_… 用户亲自输入 6 位新密码
                                └─▶ /api/security 校验并消费凭证 → scrypt 落库
```

模型能做的只有"发起"。它看不到旧密码，也不接触新密码。

**实现要点**

1. **`inputSchema` 必须保持为空对象。** `tests/password-change.test.ts` 有一条断言专门守这个契约：一旦多出 `password`/`newPassword` 字段，测试立刻失败。
2. **凭证消费与待确认动作是同一套模式**：条件更新 + `returning()`，并发重复提交只有一个成功。
3. **审计只记"发生了什么"**：`tx_password_set` 载荷只含 `{ via: 'agent_confirmation', actionId }` 或 `{ via: 'settings' }`，**不记新密码，也不记它的哈希**——审计表要长期保留并整链校验。

### 2026-10-13 · #8 常设授权与周期转账（方案 B）✅

用户一次红色强验证，授权在有限期内按周期向固定收款人转固定金额，期间不再逐笔确认。例：每月 15 日给孩子转 1500 元生活费，授权 30 天。

**"30 天内最多一次"的落地**：采用方案 B——授权期内可按周期多次执行，但有单次金额、次数、累计、最小间隔四项硬上限，到期或撤销后失效。

```
创建  "每月给孩子转 1500 生活费"
  └─▶ create_standing_mandate（红色）→ 确认单列明：每次金额 / 频率 / 授权期 / 最多次数与累计上限 / 最小间隔
        └─▶ 用户完成独立页面要求的强验证（指纹 / 人脸为模拟演示）→ bank_standing_mandates（不扣款）
执行  worker 每 10 秒扫描（或后台推进时钟）
  └─▶ runDueMandates → 逐项检查 → settleTransfer，额度扣减在同一个结算事务内
```

**硬约束（都由代码强制，不依赖提示词）**

| 约束 | 实现 |
|---|---|
| 单次上限 | 每次执行恰好转 `amountCents`，创建时 ≤ ¥20,000 |
| 次数上限 | `maxExecutions`，由有效期内的实际执行次数推导，模型传入更大值会被压回，≤ 31 |
| 累计上限 | `maxTotalCents = 金额 × 次数`，≤ ¥100,000 |
| 最小间隔 | 由频率推导（日 20h / 周 144h / 月 648h），**不是模型参数**；即使下次到期时间被改写也不会连续执行 |
| 授权期 | 1–90 天，默认 30，自确认起算 |
| 同时有效数 | 每用户 5 个，发起阶段就提示，不让用户白做一次强验证 |
| 收款人锁定 | 账号 + 户名 + 银行的指纹；变化即暂停，不转向新账号 |

**红线（改动前必读）**

1. **模型没有任何触发执行的入口。** 工具只有 `create_standing_mandate`（红）、`list_standing_mandates`（绿）、`revoke_standing_mandate`（黄）。`tests/standing-mandate.test.ts` 断言工具集里没有名称含 mandate 且含 run/execute/trigger/now 的工具。
2. **额度扣减与扣款同一个事务。** `settleTransfer` 的 `onSettled` 里条件更新授权行（状态、已执行次数、累计、授权期），不满足就抛错，整笔回滚，未扣款。`(mandateId, seq)` 唯一索引保证同一期不会执行两次。
3. **撤销与执行互斥。** 撤销是条件更新 `status`，执行的结算事务要求 `status='active'`；并发时已撤销的授权不会扣款（有测试）。
4. **创建只能在强验证之后。** `createMandate` 要求 `ctx.authorization.level === 'red'`，该字段只由确认服务写入；`authorized_action_id` 唯一，一笔确认只能产生一份授权。
5. **撤销只要求已登录。** 停止不设门槛；`/api/mandates` 没有创建和执行入口。

**执行时的复判**：授权本身就是红色强验证，所以执行时不会再要求确认。`decide()` 仍然会跑，目的是让"拒绝类"规则（熔断、账户锁定）继续生效，并在决策链里留下 `mandate_execution` 阶段的判定。余额不足等失败 6 小时后重试，连续 3 次暂停并通知。

### 11.0 两条判据（用它筛掉一半风险）

这 9 个功能里有 5 个会以某种形式碰到安全边界。用两条判据过一遍就不会出错：

1. **模型可以提供「事实」，不能提供「策略」。**
   "收款人是新客户""这笔金额异常"是事实——可以来自模型，因为它进入 `PolicyFacts` 后仍由 `decide()` 决定等级。
   "这笔需要人脸"是策略——**只能来自 `policy/rules.ts`**，一旦让模型决定等级，§0 就塌了。

2. **任何模型生成的文本都不能进入证据集。**
   数字核验的可信出处**只有三种**：服务端会话快照、本轮工具输出、服务端执行回执。
   模型写的摘要、画像、记忆总结**一律不能**作为出处——否则它会变成一条绕过 `verify/numbers.ts` 的幻觉通道。

记住这两条，下面每一项的结论都能自己推出来。

### 11.2 P0：先做这两项

#### #4 转账强验证独立链路 —— **已经实现了，你需要的是确认它**

这一项已经是本项目的核心机制，**不需要开发**：

```
模型调 transfer()
  └─▶ policy/engine.ts 判定 🔴
        └─▶ pending_actions（HMAC 绑定参数）
              └─▶ 返回 needs_confirmation 给模型
                    └─▶ 用户点确认 → 独立安全页完成对应验证 → POST /api/confirm
                          校验卡密码证明 / verifyStrongStepUp（按本次操作限制验证方式）
                          └─▶ 原子消费 → 执行
```

"独立链路，Agent 无能力越过"体现在三处，**开发时不要破坏它们**：

1. `buildAgentTools()` 注册的工具里**没有任何确认/放行工具**——模型无法自己点确认。
2. `/api/confirm` 要 `requireSession(request)`，模型手里没有用户 Cookie。
3. 验证证明必须在独立安全流程中取得，挑战 `scope` 绑定 `action:{actionId}`，**无法跨动作复用、单次消费**。演示指纹 / 人脸凭据也有方式绑定和五分钟时效，只有显式开启演示模式才有效。

**当前转账验证规则**：常规转账在银行确认后仍需密码、短信、模拟指纹或模拟人脸之一；严格超过 3000 元或向 `suspected` 账户转账，须付款卡密码加指纹 / 人脸。风险分级和验证因子要求共同生效，不能再沿用“小额只点确认、红色任选 Passkey / 短信”的旧演示说法。

验证清单应包含常规单方式、3001 元及 `suspected` 账户的双重验证；演示环境明确标注模拟，详见 `DEMO.md` 第一节。

#### #8 定时任务 + 长期授权 —— 复用现有机制，价值最高

**这项看似最大，其实最接近完成。** 现有 `scheduled_tasks` 表 + `runAutomaticTransfers()` + `bankTaskPermissions` 已经实现了 90% 的机制：

- 任务创建时记授权等级（`bankTaskPermissions`）
- worker 到期执行，**执行时重新采集事实并复判风险**；超过已授权等级则挂起要求重新确认
- 结算与成功状态**同事务提交**，宕机恢复会作废孤儿确认单
- 没有可靠标记的旧版任务不自动重跑

**缺的是三件**：

| 缺口 | 说明 |
|---|---|
| **常设授权 UI/工具** | 现在只能靠 Agent 对话创建，没有"给孩子每月发 1500 生活费，授权 30 天"这样的表达入口 |
| **周期表达** | `scheduled_tasks` 只有 `dueAt` 单次。需要 `{ every: 'monthly'\|'weekly', on: 5, at: '09:00' }` 这类极简周期描述——**不要引入完整 cron 库** |
| **次数/总额上限** | 当前只有"等级授权"，没有"次数与总量"的硬上限 |

**"30 天内最多一次"这个需求有歧义，必须先澄清**——两种读法安全含义完全不同：

| 读法 | 含义 | 风险 |
|---|---|---|
| A | 认证一次 → 30 天内**只允许执行一次**转账 | 安全，但几乎没用（发生活费是每月一次，勉强够） |
| B | 认证一次 → 30 天内**可多次执行**，但有总额上限 | 实用，但"多次"必须有硬上限兜底 |

**推荐 B + 硬上限**，且授权对象必须是一个结构化的**常设授权（standing mandate）**：

```
standing_authorizations {
  id, userId, payeeId,
  maxPerExecutionCents,   // 单次上限
  maxTotalCents,          // 授权期内总额上限
  maxExecutions,          // 授权期内执行次数上限
  intervalDays,           // 最小执行间隔（防一天内刷完）
  expiresAt,              // 到期时间
  status, revokedAt
}
```

**红线（三个"不能"）**：

1. **执行必须由 worker 触发，模型不能按需触发。** 模型可以创建、查询、撤销授权（红色强验证），但**不能**"现在就执行一次"——否则它又获得了资金操作能力。
2. **每次执行都要走 `decide()` 复判**，并且**单次与累计上限必须由代码强制**，不能只写在授权里当说明。
3. **撤销必须立即生效且可审计。**

**工程量**：约 3–4 天（授权表 + 工具 + 周期调度 + 任务中心 UI + 上限校验 + 测试）。

### 11.3 P1：价值高，但必须先守住红线

#### #1 大额陌生转账 AI 风控分析 —— **最容易把架构讲反的一项**

> 2026-10-13 已按下面的形态 D 完成；实现及验证见 [RECIPIENT-RISK.md](RECIPIENT-RISK.md)。以下保留为设计依据。

用户的直觉是"让 AI 判断这笔有没有风险"。**但风控等级只能由代码判定（§0 约束 1）。**

如果实现成"模型输出风险分 → 决定要不要人脸"，你在答辩时就把自己最强的技术优势讲反了：评委会以为你的风控是模型判断的、可以被提示词绕过。

**允许的三种形态**（都在边界内）：

| 形态 | 说明 | 复杂度 |
|---|---|---|
| **A. 纯解释**（推荐先做） | 模型生成一段**结构化风险说明**显示在确认卡上（"该收款人 3 天前新增""金额是您日常转账的 8 倍"），**不影响等级** | 低 |
| **B. 事实供给** | 模型输出**结构化事实**（`aiRiskFlags: ['收款人新增', '金额显著偏离历史']`）写入 `PolicyFacts`，再由 `rules.ts` 里一条**能升不能降**的规则使用 | 中 |
| **C. 咨询顾问** | 复用 §5.1 理财专家的只读形态：模型只读工具 + 结构化 verdict，不碰写路径 | 中 |

**绝对不要做**：模型直接返回 `level: 'red'`，或模型返回的风险分参与 `maxRisk()`。等级必须由 `rules.ts` 用事实算出来。

**注意形态 B 的措辞**：规则要写成"当 `facts.aiRiskFlags` 非空时升级为红色"——**策略仍然在代码里**，模型只贡献了"这笔像不像异常"这个**事实**。这和"新收款人升级"是同一个模式。

**性能警告**：这会在**确认路径上**加一次模型调用。确认路径必须快，建议异步生成、卡片先出，"AI 分析"作为补充信息后到。

**形态 D：后台智能体标记收款方（2026-10-12 追加，推荐，取代形态 A 作为首选）**

不让面向用户的 Agent 评定风险，改由后台智能体在 worker 中异步分析收款账户，写入风险标记；用户发起转账时 `collectFacts()` 读标记，`rules.ts` 决定升级。

```
worker：SQL 算结构化特征 → 模型给判断与理由 → bank_risk_flags（suspected）
                                                    └─▶ 后台人工复核 → confirmed / 解除
用户转账：collectFacts 读 payeeRiskFlag → rules.ts：suspected 升红色并提示；confirmed 拒绝
```

优点：用户对话注入不到它；确认路径只多一次查表；标记落库可审计。

四条约束：

1. **AI 只能加标记，不能摘标记**；解除只能由后台人工操作。
2. **AI 标记（`suspected`）只升级为红色，不直接拒绝**；人工复核为 `confirmed` 后才允许拒绝。误判的代价应是"多验证一次"，不是"转不进钱"。
3. **特征由 SQL 计算**（开户天数、短期内不同付款人数、快进快出比例等），模型不读原始备注与商户名，避免间接注入。
4. **给付款人的提示不下定论**："该收款账户近期收款特征异常，请核实对方身份"。

局限：异步分析有时间差，全新账户的第一笔仍靠既有"新收款人升红色"规则兜住，两条规则互补；演示数据中没有欺诈模式，需要专门补"骡子账户"种子数据。

**已定（2026-10-12）：做完整版**，即 `suspected` 与 `confirmed` 两级都实现，含后台复核视图。验收点：

- AI 标记后，向该账户转账升为红色，确认卡出现核实提示；
- 后台复核视图能看到特征与理由，可"确认高危"或"解除"，两种操作都写审计；
- 确认高危后，向该账户转账被策略拒绝，决策链里能看到命中的规则；
- 没有任何路径能让模型降低或删除标记（需有测试守住）；
- 已有待确认单在标记之后确认时，按执行时事实复判（现有 `confirmPending` 机制，补一条用例）。

改动点：新表 `bank_risk_flags`（账户、级别、特征、理由、来源、复核人）；`PolicyFacts.payeeRiskFlag` 与 `facts.ts` 查表；`rules.ts` 新规则；worker 分析步骤；后台复核视图。与 #7 用户画像共用同一条流水线，建议一起做，合计约 3–4 天。

#### #2 上下文压缩 —— **做错了会成为幻觉通道**

现状：客户端每轮提交完整历史（`ChatView` 的 `useChat`），服务端**完全没有历史存储**。历史长了就越来越慢、越来越贵。

**最大的坑**：压缩会产生一段**模型生成的文本**。如果这段文本进入 `collectEvidence()`，那么"上个月余额 5000 元"这句话就会让模型正文里的 `5000` 通过数字核验——**幻觉通道就此打开**。

**必须遵守**：

1. 压缩摘要**永不进入证据集**。`agent/run.ts` 的 `evidence` 数组只能来自服务端快照、本轮工具输出、执行回执。
2. 保留最近 N 轮**原文**（建议 6–10 轮），只压缩更早的。
3. `⟦外部文本⟧…⟦/外部文本⟧` 隔离标记必须原样保留——压缩时丢失标记，等于把备注/商户名升级成可信指令。
4. 压缩后的历史里不能有"已完成转账"这类**看起来像事实的陈述**，否则模型会据此认为已经办过。

**顺带修一个已发现的隐患**：`runAgent()` 的 `priorEvidence` 参数**从未被使用**——`chat.ts:45` 和 `lark.tsx:54` 都传了值，但 `run.ts` 里只 `const { ctx } = params`，从未读取。它的 JSDoc 还写着"作为数字校验的补充出处"，与下面那行注释（"浏览器提交的历史工具结果不是银行凭证"）自相矛盾。

**这是误导性的死参数**：将来有人看到它，会以为历史正在参与核验，甚至可能"修复"成真的启用它——那就直接打开了幻觉通道。建议连同 `messages.ts` 的 `historyEvidence()`（唯一用途就是喂给它）一并删除。

#### #5 简易智能交互界面

即 §5 里建议的 genui 扩充，**现状约完成一半**：`show_view` + `catalog.ts` + `registry.tsx` + 服务端 `checkSpec` 已经可用，但 `catalog.actions = {}`，只有 `FollowUp` 能发消息，用户看得到图但**改不了参数**。

要补的组件（**全部保持"只提交数据、不执行写操作"**）：`AmountInput`、`AccountPicker`/`CardPicker`、`StepList`（DAG 进度）、`KeyValue`、`Timeline`。

**红线**：目录里**永远不出现** `submit_action`、`confirm`、`pay` 这类 action。任何"确定"按钮只能生成一条**新的用户消息**，重走完整流程。

另需补：组件树**节点数/深度上限**（现在没有）、校验失败率**可观测性**（加 `view_rejected` 审计计数）、Top 3 场景的**兜底模板**。

#### #7 后台用户画像

后台是**人工直连通道，不经过策略引擎**（§7 第 10 条），所以这项**不触碰授权边界**，可以做。

**唯一红线**：画像里的数字必须**由 SQL 确定性算出**，模型只负责写文字；且文字中出现的金额必须来自已算出的集合（与 genui 的"禁止数字字面量"同源）。

数据来源已经齐全：`transactions`（分类/时间/对手方）、`accounts`、`holdings`、`products`、`cards`。建议先做**确定性指标卡**（月均支出、储蓄率、消费结构、风险等级），再叠加"AI 点评"。

**顺带**：`listAdminUsers()` 目前只汇总账户数与总余额，`riskLevel` 直接取 `users.riskRating`。画像是它的自然延伸。

### 11.4 P2：可以做，但别指望"防住"

#### #6 对话历史查询与记忆

现状：**服务端没有对话历史表**。Web 靠客户端每轮提交，飞书存在进程内 `Map`（重启即失）。`agent/session.ts` 的 `store` 也是进程内 Map。

要做需要新表：`chat_sessions` / `chat_messages`，以及给飞书复用的服务端历史。

**红线**：**记忆只能存偏好与事实，绝不能存余额、持仓、执行结果。** 一条"用户上次查到余额 5000 元"的记忆，在两周后就是一条过期的幻觉源。记忆和压缩摘要属于同一类东西——**先进模型上下文，永不进证据集**。

**与 #2 的关系**：#2 是"历史太长怎么压"，#6 是"历史存哪"。**先做 #6，再做 #2** ——服务端有了历史，压缩才有稳定的落点，否则你要在客户端做压缩，等于让浏览器决定服务端看到什么。

#### #3 防止被调用于其他用途

**先说结论：无法完全防住，也不该按"防"来做。**

这是个通用 LLM 的固有问题。用户让 Agent 写代码，模型会写——`/api/chat` 没有任何机制阻止它。可做的：

| 手段 | 有效性 | 说明 |
|---|---|---|
| 指令层声明用途 | **弱** | 会被绕过，不要当防线 |
| **每用户请求/Token 配额** | **强** | 这才是真正的业务控制——成本可控，滥用无收益 |
| 意图拒答 | 中 | 需要判意图，而判意图本身可能被绕过 |
| 异常用量审计 | 中 | 突增请求量写审计并告警 |

**推荐**：配额表（`user_quotas`：日请求数、日 Token 数）+ 超限拒绝 + 审计。**在答辩时说"我们通过用量配额控制滥用成本"，比承诺"我们防住了提示词绕过"更可信**——后者做不到。

注意 `auth.ts` 的 `rateLimit` 只覆盖**认证端点**；`/api/chat` 目前无限流。

### 11.5 P3：最后再做，且必须复用 #8 的原语

#### #9 创建 AI 子账户（自动理财、管理费用、自动生活缴费）

**最有想象力，也最容易毁掉整个叙事。**

「AI 子账户自动理财」的字面实现 = 让模型决定"现在该买哪只理财" → **这就是让 LLM 移动资金**，与 §0 直接冲突。

**唯一正确的形态**：用户**一次性**把自己的意图翻译成一条**确定性策略**，之后由 worker 执行，模型不再参与每一笔决策。

```
用户："工资到账后，超过 5000 的部分自动买 R2 以下的理财"
  └─▶ 模型把这句话翻译成结构化策略（一次性，红色强验证 + 确认卡）
        └─▶ standing_policy { trigger: 'salary_in', threshold: 500000, 
                              action: 'purchase', maxRisk: 'R2', maxPerMonth: ... }
              └─▶ worker 按月执行，每次走 decide() 复判
                    └─▶ 模型从此不再参与
```

**看清这一点：这本质上就是 #8 的常设授权，只是触发条件从"时间"变成"事件"。**

所以 **#8 是 #9 的前置**——先把 `standing_authorizations` 这个原语建好，再加"事件触发"这一维。**不要为 #9 单独造一套机制**，否则同一个安全属性会有两份实现、两份漏洞。

**管理费用**是个好设计（给"银行"一个商业模式），但要明确它是**从子账户余额按比例扣**的确定性规则，不是模型决定的。

**工程量**：授权原语建好之后，还要 4–6 天（事件触发 + 子账户账务 + 上限校验 + 测试）。**11.02 之前不要开工。**

### 11.6 #10 中途终止任务（2026-10-12 追加）

对应赛题"执行过程中支持中断、回退和人工接管"。

**现状（已核对源码）**

| 层 | 已有能力 | 位置 |
|---|---|---|
| 对话 | 停止按钮，中断模型流 | `ChatView.tsx` 的 `stop()` → `request.signal` → `streamText` |
| 计划（DAG） | 暂停、恢复、取消并逆序补偿、人工节点处理、失败后记录人工核对 | `executor/service.ts` 的 `controlPlan`、`/api/plans`、`TaskCenter.tsx` |
| 单笔确认 | 取消确认单；关联计划同时回退 | `cancelActionAndPlan`，飞书卡片也有取消按钮 |
| 定时任务 | 取消未执行的任务 | `cancel_scheduled_task`、`cancelScheduled` |

**缺口**

1. **停止按钮停不住计划。** `advance()` 不接收中断信号，`plan_task` 一旦开始会跑到挂起或完成并落库。用户按了停止后收不到计划卡片，这个计划只能在任务中心里发现。停止本身也没有写审计，只有一行 `console.info`。
2. **运行中的计划无法暂停。** `startPlan` 在 `advance` 全部跑完后才落库，期间 `controlPlan` 读不到它。暂停实际只在挂起点生效。
3. **对话里停不了。** Agent 只有 `cancel_scheduled_task`，没有查询、暂停、取消计划的工具，用户说"算了别办了"无法处理。
4. **没有一键急停**，也没有飞书侧的计划级暂停/取消，后台只能逐个取消任务。

**原则**

- **停止不设门槛，继续才要验证。** 暂停和取消只要求已登录；恢复时按执行时事实重新过策略（现有 `confirmPending` 已如此）。
- **暂停不等于回退。** 暂停只停后续步骤；取消才触发补偿，取消前要列出会冲正哪些步骤、哪些无法回退。
- **已提交的资金结算不可中断。** 定时任务处于 `processing` 时不提供中止，只能事后冲正。这是现有设计，不要改。
- **不给模型恢复类工具。** 恢复走任务中心或确认卡。

**分步计划**

| 步骤 | 内容 | 工期 |
|---|---|---|
| S1 | 停止按钮接通计划：中断信号经 `buildAgentTools` 传到 `startPlan` 和 `advance`，在节点之间检查；命中则置为 `paused` 并落库，写 `plan_control` 审计；`ChatView` 停止后刷新计划并给出"已暂停的计划"入口 | 0.5 天 |
| S2 | 计划先落库再推进：`startPlan` 先保存初始状态，每完成一个节点保存一次并重读状态，使暂停能在节点之间生效。`startPlan` 目前没有拿 `plan:{id}` 锁，需要补上，否则会与 `controlPlan` 互相覆盖 | 0.5 天 |
| S3 | 对话工具：`list_plans`（只读）、`pause_plan`、`cancel_plan`（写操作，黄色确认，摘要列出将冲正和无法回退的步骤）。`tests/planning-tools.test.ts` 要求写工具不能是绿色，所以这两个都走确认 | 1 天 |
| S4 | 一键急停：`/api/plans` 增加 `stop_all`，暂停全部进行中的计划、作废全部待确认单；任务中心加入口。定时任务目前没有"暂停"状态，要加的话需同步修改 worker 的查询条件，建议与 #8 的常设授权一起设计 | 0.5 天 |
| S5 | 飞书文本指令"暂停计划/取消计划"由代码匹配，不经模型；后台增加"冻结该用户的自动化" | 0.5 天 |

## 12. 剩余任务的复杂度与模型选择

> 2026-10-13 评估。用于决定每项任务交给 Claude Opus 5.5 还是 Claude Sonnet 5.5、用哪档思考等级（effort）。

### 12.1 评级标准

复杂度看的是**改错的后果**和**需要同时记住多少约束**，代码行数是次要的。

| 复杂度 | 判据 | 模型 | effort |
|---|---|---|---|
| **简单** | 不碰授权、资金、事务；改错了测试或肉眼能立刻发现 | Sonnet 5.5 | `low`（文档、文案）/ `medium`（小段代码） |
| **中等** | 有业务逻辑或 UI 状态，但不改变"谁能做什么"；有现成模式可照抄 | Sonnet 5.5 | `medium`，状态多时 `high` |
| **复杂** | 碰到 §1 硬约束或 §11.0 两条判据，或涉及事务、并发、跨进程 | Opus 5.5 | `high` |
| **极其复杂** | 新建授权原语或资金自动执行路径；错误会在之后多个功能里被复用 | Opus 5.5 | `xhigh`；设计和最终审查可用 `max` |

两个模型的取舍：

- **价格**：Opus 5.5 每百万 token 输入 $4 / 输出 $20，Sonnet 5.5 为 $2 / $10，Opus 约为 Sonnet 的 2 倍。
- **默认 effort 不同**：Opus 5.5 默认 `medium`，Sonnet 5.5 默认 `high`。上表的档位请**手动选定**，不要依赖默认值。
- **Sonnet 5.5 的档位是重新校准过的**：日常编码从 `medium` 起步即可，不必照搬旧 Sonnet 的习惯一律开 `high`。
- `max` 只在"错一次代价远高于多花的钱"时用，例如 #8 的授权原语设计。日常实现开 `max` 多半是浪费。

**一条通用做法**：凡是 Sonnet 实现、但碰到了 §1 或 §11.0 的改动，合并前用 Opus 5.5（`high`）跑一次 `/code-review`。审查比从头实现便宜得多，又能补上 Sonnet 在长约束链上的疏漏。
